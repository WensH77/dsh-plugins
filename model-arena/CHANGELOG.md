# Changelog

本文件记录 `dsh-plugin-model-arena` 的历次改动决策（内部里程碑 v3–v28）。安装、使用、架构、测试见 [README.md](./README.md)。

## 决策记录

- **业务探索主模型 persona 允许逐条修正、不认可可用 ask_user_question 提出（v34 → 0.7.3，纯浏览器端）**：按用户指示，`buildMainRoleSeed` business 分支（默认分支，Technical Expert）由「再针对挑战者的质疑进行修正」改为「再针对挑战者的质疑逐条修正，但不必全盘接受质疑，如有不认可的条目，可以使用ask_user_question工具提出」——主模型不再全盘接受挑战者的质疑，可对不认可的条目用 `ask_user_question` 与用户确认（平台 v8 `hasPendingInteraction` 守卫保证提问不中断流程、不会误判停止）；qa 协作者/知识沉淀 persona 不变。测试：client-smoke 新增 1 条断言（business main seed 含「逐条修正」「不必全盘接受质疑」「ask_user_question」且不含旧措辞「进行修正」）。依赖：client 改动刷新生效。

- **persona 改为双会话版——verdict 三分支处理、不照搬竞技场 V2 的工具派遣（v33 → 0.7.2，纯浏览器端）**：按用户指示（「我要你把提示词改为双会话版本」，驳回照搬 v2 的 `arena_review` 工具版；随后按用户最新一版提示词定稿），`buildMainRoleSeed` knowledge 分支替换为**适配 v1 双会话机制**的角色指令——intro 改为「你是 Knowledge Expert，是 Theseus workflow 的主执行者，但 review 阶段由挑战者独立执行」；propose 完成并获用户确认后 **record propose.completed，随后停止本回合**，等待竞技场挑战者会话（不同模型、独立上下文）执行审查：挑战者读取产物文件、按审查规范写出 review.md（含 Action Items）并返回一行 Overall Verdict，审查结论以**用户消息注入本会话**（v1 的 node 半段检测 propose.completed → 浏览器编排挑战者会话 → 注入简洁「审查结论：不认可/认可」）；收到注入 verdict 后先读 review.md 核对 Action Items，按三条分支处理：NEEDS_REVISION（「审查结论：不认可」）→ 汇报询问 → 修正 → 重新按第 2 条询问后重新提交审查（再次 record propose.completed 送审），最多 3 次、累计 3 次不认可后审查循环结束、停下汇报等人工；NOT_READY（「审查未通过/不完整」）→ 汇报询问 → record review.completed NOT_READY（状态停留 review）→ 重新提交审查，计入 3 次上限（v1 挑战者暂不输出 NOT_READY，该分支为 Theseus 语义防御）；READY（「审查结论：认可」）→ 先汇报审查结论、询问用户确认后再 record review.completed READY 并按 Theseus workflow 继续；**第 4 条「后续 user-readiness-review / apply / archive 按 Theseus workflow 推进，每个环节完成时先向用户汇报、调用 ask_user_question 询问确认后再继续」**；**新增第 6 条回合停止规则：所有确认节点（explore/propose/修正确认/READY/readiness/apply/archive）一律调用 ask_user_question 提问、用户回答后在同一回合内继续推进，不因询问而停止回合或结束会话——唯一回合停止点是第 2 条 record propose.completed 后等待挑战者审查**（修复用户实测「主模型没有 ask user 而是结束会话」：persona 此前只写「询问用户」未写明工具与不停回合语义；平台 v8 的 `hasPendingInteraction` 守卫本就保证提问不中断流程、不会误判停止，问题在 persona 措辞）；第 5 条去掉「你只负责 explore、propose 与审查通过后的继续」职责收口，仅保留挑战者独占审查禁令。**与 v2 的边界**：v1 双会话版不含 `arena_review` 工具、不含 `fixSummary` 参数（那是 v2 单会话工具派遣机制的专属），主模型不调用任何工具，只靠注入的 verdict 用户消息分流。**相对 v32 的行为回退**：READY 不再「收到即继续、无需再询问」，改回「先汇报审查结论、调用 ask_user_question 询问用户确认后再 record review.completed READY」；readiness/apply/archive 每环节依旧需要用户确认——注入文本（用户消息）是明确信号，persona 指令明确要求调用 ask_user_question 询问用户，不存在 v32 的「注入算不算用户确认」歧义。测试：client-smoke persona 断言更新——「启动workflow」→「启用workflow」；删除「无需再询问」与 arena_review/fixSummary 断言，新增双会话语义断言（propose 后停止本回合、等待挑战者会话、verdict 用户消息注入、不出现 arena_review/fixSummary、ask_user_question 覆盖全部确认节点（≥6 处）且回答后继续本回合、唯一回合停止点是第 2 条 propose 后等待挑战者审查、第 4 条每环节询问确认后再继续且不含「由 Theseus 流程自身负责」、第 5 条无「你只负责」职责收口）与三分支断言（共 11 条）。依赖：client 改动刷新生效。

- **移除「最高优先级强制约束」框架，persona 写明负责 step，READY 后主模型不再「天人交战」（v32 → 0.7.1）**：用户实测知识沉淀会话——挑战者返回 READY 后，主模型因 v31 逐阶段询问约束（READY → 先汇报并询问是否继续；readiness/apply/archive 每阶段再询问）反复自我辩论「注入的『审查结论：认可』算不算用户确认」，流程停滞。修复两处：(1) **persona 重写**——`buildMainRoleSeed` knowledge 分支去掉「【最高优先级强制约束】」前缀与禁令罗列式措辞，改为平实职责陈述并**写明负责的 step**：explore、propose，以及方案通过挑战者审查后 record review.completed READY 并按 Theseus workflow 继续后续阶段（user-readiness-review → apply → archive）；收到简洁「审查结论：认可」即按 persona 职责直接继续、**无需再询问**（READY 的继续授权写进 persona 而非注入指令）；readiness/apply/archive 不再 persona 级重复询问（用户确认由 Theseus 流程自身环节负责）；explore/propose 仍保留「先汇报并询问用户」（用户确认）；NEEDS_REVISION 仍汇报 Action Items 并询问是否修正；review 由挑战者会话独立执行不变（不 auto-advance 到 review、不执行 theseus-review-spec、不写 review.md / 不给出 Overall Verdict）。(2) **注入保持简洁**——READY 注入文本不变（`审查结论：认可`，两处：前台 `advanceReview` 与后台 `advanceBackgroundDuels`），对话流不显示指令性注入，主模型凭 persona 职责即可继续。测试：client-smoke 新增 4 条 persona 断言（无「最高优先级强制约束」字样、写明负责 step（record review.completed READY + user-readiness-review/apply/archive）、认识简洁「审查结论：认可」并「无需再询问」、保留 explore/propose 询问与挑战者独占审查）；既有 READY/NEEDS_REVISION 注入断言零改动。依赖：client 改动刷新生效。

- **新增 `/arena` 斜杠命令——父子级联选择（0.7.0，纯浏览器端）**：按用户指示「不让用户手输参数，改为弹窗选择，model/effort/scene 三要素都必须有有效值」，并在评审中进一步要求「做成父子选择器、不要拍平」。dsh 原生命令弹窗（popupSelect）是**单层结构**（SelectOption 无嵌套/分组字段、options 每打开只取一次、选中即关闭），装不下级联，故采用**混合方案**：(1) **第 1 步用原生弹窗选场景**（业务探索/知识沉淀/测试用例三行，场景不依赖模型；原生壳 settle 时自动消费输入框里的 `/arena` token，无残留）；(2) **第 2-3 步用自绘级联面板**（注册在公开的 `conversation.input.overlay` 槽位，list 型、与原生命令弹窗共存；浮于 composer 上方，交互与 hero 面板「模型 → 推理等级」两级菜单一致：按提供方分组、输入框当前模型被排除、推理等级用该模型自己的 efforts、无推理等级模型点选即用默认；支持 ↑↓/回车/Esc 键盘、点外部/✕ 取消，Esc 取消不产生任何变更）。**零 node 改动**、全同步应用（`applyArenaSelection`）。对比初稿的「组合行拍平」：用户在评审时否掉手输参数（host 命令 + settings round-trip 全删），又否掉组合行（原生壳单层限制），最终定型为「原生场景弹窗 + 自绘级联面板」；不 shadow `commandUi` 派发、不碰内部 `slash/input-consume-token` 事件（脆弱路径），token 由原生壳消费，自绘部分只依赖公开槽位。冻结语义沿用：竞技场会话创建后拒绝重配（`slash.frozen`）。浏览器端 inject 增加 `commandUi`（package.json `dsh.client.inject` 同步）。测试：client-smoke 新增纯函数（`buildArenaModel` 推理等级归一化、`applyArenaSelection`）+ contribution 集成（场景弹窗三行、onSelect 打开级联面板、模型步排除输入框模型/按提供方分组、推理等级步列出模型自己的 levels、点选后同步应用 + composer 解锁、Esc 取消不生效、冻结态拒绝、随后首问按所选场景/模型/推理等级启动挑战）；测试桩 document 增加监听捕获（dispatchDoc）以驱动 Esc 取消路径。
  - **实测修复（同一版本内）**：(1) **级联面板不显示 bug**——`SlashWizardView` 的 `useEffect` 依赖原为 `[sessionId]`，但承载面板的宿主 div 是打开后才渲染的（ref 由 null 变 div 时 effect 不会重跑），导致选完场景后面板从未挂载、宿主 div 为空；修复为依赖 `[sessionId, state]`（每次 label 挤到省略；改用独立的 `scene.popup.X` 简写描述（**不以场景名开头**），并调整为差异化开头（「挑战式探讨 / 方案审查 / 用例验收」）消除同质化；级联面板 z-index 提到 120（高于原生弹窗 100），过渡瞬间不被遮；(3) **选完场景直接跳推理等级步**——键盘监听挂在 document 且 Enter 会点 `rows[activeRow >= 0 ?
