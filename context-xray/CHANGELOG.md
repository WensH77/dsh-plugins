# 变更日志

## 0.1.0

首个版本（尚未提交，改动都并在这里）。

**产出**

- `context_xray` 工具：分析当前会话或指定活跃会话的上下文归因，输出 markdown 报告（来源占比条形图、强度榜、时间分布表、关键词表、从未被提及的块）。参数 `session` / `limit` / `matrix` / `minTerms`。
- 离线入口 `tools/xray.mjs`：直接读会话 jsonl（zstd），可指定会话、工作区或文件，支持 `--json`。
- 归因核心 `lib/mention.js`：按来源拆上下文块，`Intl.Segmenter` 中英混合分词，停用词过滤，df 加权 + 长度归一。
- 渲染 `lib/render.js`：tool 与 CLI 共用，含 CJK 宽度对齐的 markdown 表格。
- 19 项 smoke 测试。

**修正过的口径问题**（都在开发期内发现并改掉）

- 矩阵曾按「词在上下文块里的出现次数」排序，却展示「在 reasoning 里被提及的次数」，两个数字无关——代码里的 `const` 因为满屏都是而排第一，实际只被提及 1 次。改为按展示的提及列排序。
- 弱归因高估：词在块内只出现一次却享全额归因权重（`logic`：1 个块 × 1 次出现 → 102 次提及）。改为按出现次数折扣计权。
  先用的是「出现次数 < 2 就不参与归因」的硬过滤，结果把短块（含会话起因那条用户消息）的 `terms` 清零、误判成「从未被提及」，死重清单从 4 个炸到 154 个。改为折扣后词集不被破坏。
- 矩阵补齐两列：该词在上下文里的出现次数、贡献最大的来源块（把「词」和「块」接起来）。
- 停用词补充一批通用英文词（`need` / `through` / `logic` / `use` / `make` 等），此前它们漏网后冒充成了块的特征词。

**可读性改造**

- 时间轴压到固定桶数（默认 40）并配早/中/晚三段占比 + 峰值步，此前 180+ 步的 sparkline 一行能到 240 字符。
- 「主导来源切换」那串逐步抖动（实测 138 次）改成只列连续主导 ≥ 4 步的段落（实测剩 2 段）。
- 每个块带稳定编号（`#544`），三个同名的「工具结果：bash」从此可区分、可互相引用。
- 关键词与强度榜改成表格，列一列一个指标；重复的死重块合并计数（5 条空参数的 `list_agents` 合成一行）。
- 条形图定宽对齐，百分号不再随条形长度参差；预览里的绝对路径折叠成 `~/`（每个 bash 入参都以 `cd /Users/…` 开头，白占十几个字符）。

**归因力**（新增列）

- 定义 `min(提及, 上下文) ÷ 跨度`：分子取两者较小者，避免被我的口头词（提及 > 上下文）或上下文填充词（上下文多但跨度大）单独带偏。
- 配最小跨度门槛，且**随 reasoning 轮数缩放**（`max(2, round(轮数 / 40))`）。实测 107 步 → ≥3 挡掉 313 个词，148 步 → ≥4，183 步 → ≥5 挡掉 1191 个。固定门槛在短会话里太严、长会话里太松。

**体积与累计**（并入同一套块模型）

- 原先 `lib/report.js` 单独做过一套按真实 usage 校准的 token 计量，但它把 reasoning 也算成块、与 `mention.js` 的块模型不同，两边的块无法按索引对齐。改为把计量逻辑并进 `lib/mention.js`：`split()` 同时产出块、reasoning 与请求面（含 reasoning，它会被回传、同样计费），据此按步校准。`lib/report.js` 删除。
- 新增两列：**体积**（该块在末次 prompt 里的 token 数）与**累计**（整个会话为它付的总账，每步重发都算）。两者差距越大，越说明它是被反复重发的固定成本。
- 来源占比从单口径扩成三口径并列：提及 / 体积 / 累计。实测差异极大（某会话 tool-result 提及 33.8% 但体积 81.9%）。
- 报告头部新增末次 prompt 规模与窗口占用率。

**未闭合的用户输入**（新增视图）

- 抓「你说了、但在那一轮既没被想也没被答」的词：窗口按这条用户消息到下一条用户消息之间取，不是整个会话——否则后面几轮提到过就算覆盖，前面被丢掉的要求会被洗白。
- 已知假阳性：**指令类词**（「用英文」「帮我」）被遵守而不被讨论，因此永远不出现；用户消息里的拼写变体与缩写也会被当词统计。停用词补了 `please` / `cannot` / `thanks` / `saw` 等口语功能词，URL 与裸域名在判据前先剥掉（否则出来的是 `https`、`stg`、`tbeng` 这类碎片）。
- 实测某会话：11 个静默遗漏词里真信号 4 个（报错原文的 `contact` / `consultations` / `granted` / `send`），其余是指令词、拼写变体和从句词。

**回复里无出处的标识符**（新增视图，第二个方向）

- 抓「我写了、但此前的 reasoning 与上下文里都没有这个写法」的可核对 token（标识符 / 路径 / 版本号 / 行号）。「有出处」按当时之前算——后面某个工具结果里出现过，不能反过来给先前那句话背书。
- 判据从词级收窄到可核对 token，是量出来的：词级匹配在英文会话报 121 个、中文会话报 154 个，样本几乎全是写报告时的措辞（`dig` / `Verified` / `caveat` / `实证` / `核实` / `I'll`）——我的回复语域和思考语域本来就是两套，词级匹配分不开。收窄后英文会话剩 3 个（`props.complianceSettings.complianceApproved` 等）、中文会话剩 2 个（`config.serverName` / `config.excludes`），全是真需要核对的。
- 代价：纯自然语言的凭空断言查不到。报告里明写了「清单空着不代表没问题」。
- 两个清单都改成「词 + 原句」两行结构：只给光秃秃的词，读的人判不了它算不算真问题。

**已知口径与偏置**（不是缺陷，是代理指标本身的性质）：提及度不等于注意力；原始提及次数有长度偏置，报告主排序用强度；小块强度虚高，用 `minTerms` 门槛挡掉；任务主题偏置无法消除；极短的用户指令（「修复」「直接提交」）在提及度上垫底，但它们往往是会话的转折点。
