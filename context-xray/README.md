# dsh-plugin-context-xray

上下文 X 光：把会话的上下文拆成块，用**各块的关键词在 reasoning 块里被提到了多少次**做归因，回答两个问题——这份上下文是被谁吃掉的，以及哪些内容从头到尾没被想起过。

因为真正的 attention 矩阵拿不到（云端 API 不返回、harness 的 ContentBlock 词汇表里也没有位置安放），这里用思维链的提及度做代理。

## 先说口径，否则数字会骗你

**这是提及度，不是注意力。** 它统计的是「我在思考时提到了什么」，不是「我在计算时看了什么」。三个指标含义差别很大：

| 指标 | 含义 | 能不能用来排名 |
|---|---|---|
| `rawHits` 原始提及 | 该块所有词在 reasoning 里出现的总次数 | **不能**。有严重长度偏置：11,798 字符的系统提示词天然压过 41 字符的用户消息 |
| `coverage` 覆盖率 | 该块有多少比例的词至少被提到过一次 | 可以，用于找「整块没被用上」 |
| `intensity` 强度 | df 加权后按词数归一化的平均提及数 | 可以，这是报告的主排序依据 |

实测对比（本仓库的一次真实会话）：按原始提及排名，用户消息只占 1.0%，看起来最不受关注；按强度排名，用户消息 8.3 排第一。**前者是错的**——41 个字符的块怎么算都赢不了 11,798 个字符的块。

已知偏置，报告里都做了处理或标注：

- **小块虚高**：词少的块每词均值天然高（9 个词的用户消息能拿 6.0）。强度榜设了 `minTerms` 门槛（默认 20 词），未达门槛的块不进榜。
- **弱归因高估**：一个词只在某个块里出现一次、却在 reasoning 里出现上百次时（实测 `logic`：1 个块 × 1 次出现 → 102 次提及），全额计入会凭空造出一个高强度块。归因对这类词按半份计权。
  这里刻意用折扣而不是过滤：把低频词从词集里删掉会同时缩小分母，让短块的 `terms` 归零、整块被误判成「从未被提及」（实测死重清单会从 4 个炸到 154 个，连会话起因那条用户消息都被算进去）。
- **任务主题偏置**：无法消除。分析上下文的任务里，上下文类词汇天然高频。换一个任务是调 CSS，同一批上下文块会得出完全不同的贡献度。
- **自指膨胀**：这个工具的输出本身会进入上下文，下次再分析时它会作为一个被高度提及的块出现。
- **遗漏与无出处各只算得出一部分**：报告里两个清单——「未闭合的用户输入」抓你说了、但那一轮既没被想也没被答的词；「回复里无出处的标识符」抓我写了、但此前的 reasoning 与上下文里都没有这个写法的可核对 token。前者看你的输入，后者只看我写的话。
  两类都算不出来的遗漏：「想过、答了、但没做到」没有可数痕迹；「该查而根本没查」连上下文都没进。
  回复侧刻意收窄到标识符 / 路径 / 版本号，因为词级匹配实测不可用——同一会话里「我写过但上下文没有」的词有 121 个，绝大多数是写报告时的措辞（`dig` / `实证` / `核实` / `I'll`），收窄后剩 3 个。代价是纯自然语言的凭空断言查不到。**两个清单都空着，不代表没有问题；而高提及 / 高体积只说明这轮在忙什么，不说明这轮成了什么。**
- **归因力的样本量**：归因力 = `min(提及, 上下文) ÷ 跨度`，跨度为 1–2 时分母接近 1，一个词偶然出现一次就能被抬成假冠军（实测 `客户` 提及 190、只出现在 1 个块里，归因力 7.00 排第一）。因此设了最小跨度门槛，并且门槛跟着 reasoning 轮数缩放（`max(2, round(轮数 / 40))`）：固定值在 100 步的会话里太严、在 200 步的会话里太松。

## 工作原理

1. **拆块**（`lib/mention.js` 的 `split`）：把事件流拆成上下文块与 reasoning 块。上下文块按来源分类——系统提示词、注入（工作区指令 / 会话引用快照 / 技能目录 / 运行时快照）、用户消息、工具结果、以及 agent 自己写进上下文的工具入参与回复正文。注入必须与用户自己发的消息分开，否则归因会把注入算到用户头上。
2. **分词**：`Intl.Segmenter`（Node 内置 ICU，零依赖）做中英混合分词，再过一遍停用词表（`lib/stopwords.js`）。
3. **归因**：一个词出现在多个块里时，命中数按出现块数分摊（df 加权），避免同一个词在每块里都记全功；词在块内只出现一次时按半份计权；再按词数归一化得到强度。
4. **体积校准**：按字符密度估出每个块与每段 reasoning 的 token 数，再用每一步 provider 报告的真实 `usage`（`inputTokens + cacheReadTokens`）校正出该步的缩放系数。某块在多少步里存在，就把那些步的消耗累加成「累计」——所以固定成本类的内容（系统提示词、工作区指令）累计会远大于它在末次 prompt 里的体积。
5. **渲染**（`lib/render.js`）：markdown 输出——来源占比（提及 / 体积 / 累计 三个口径并列）、强度榜（覆盖率 / 提及 / 强度 / 体积 / 累计）、时间分布表（早/中/晚占比 + 峰值步 + 压缩到固定宽度的 sparkline）、关键词表（归因力 / 提及 / 上下文 / 跨度 / 贡献最大的来源块）、未闭合的用户输入、回复里无出处的标识符、从未被提及的块清单。每个块带稳定编号（`#544`）以便区分和引用同名块；重复块合并计数；时间轴按桶压缩，避免长会话把一行撑到几百字符。前两个清单都给出原句——只给光秃秃的词，读的人判不了它算不算真问题。tool 与 CLI 共用这一份渲染。

提及和体积是两条独立的尺子——一个按词频算，一个按字符密度算——都校准到同一批块上，所以可以并列读：**提及高而体积小 = 那句话很关键；体积大而提及低 = 贵但没被想起**。

## 安装

```bash
dsh plugin --profile web add 'git+https://github.com/WensH77/dsh-plugins.git#path:context-xray'
```

宿主端（Node 半段）改动需要**重启 dsh web** 才生效。

## 使用

### 作为工具

注册 `context_xray`，agent 在会话里可直接调用：

| 参数 | 默认 | 说明 |
|---|---|---|
| `session` | 当前会话 | 要分析的会话 id |
| `limit` | 12 | 强度榜条数 |
| `matrix` | 10 | 关键词矩阵行数 |
| `minTerms` | 20 | 进入强度榜的最小词数门槛 |

工具只能分析**当前已加载**的会话；历史会话走下面的离线入口。

### 离线

```bash
node tools/xray.mjs                          # 最近一个会话
node tools/xray.mjs <会话id前缀>              # 指定会话
node tools/xray.mjs <文件.jsonl.zstd>         # 直接给文件
node tools/xray.mjs --workspace dsh-plugins  # 指定工作区
node tools/xray.mjs --json                   # 原始 JSON
```

## 配置

无。所有可调项都是工具参数。

```bash
node --test test/*.mjs
```

## 已知限制

- **不是注意力测量**，是提及度代理。上面的三条偏置无法消除，只能标注。
- **停用词表内置、不可配**。自定义排除词只能从代码层面加。
- **工具只能看已加载的会话**。持久化后未加载的历史会话，用离线 CLI。
- **没有做因果分析**。某块被提及不等于它对输出有因果贡献；这需要干预实验，不是统计能做到的。
- **`Intl.Segmenter` 的分词质量依赖 ICU 版本**，不同 Node 版本可能切出不同的词，跨机器对比同一会话的数字可能有小差异。
