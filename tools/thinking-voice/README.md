# 思维链语态（We need / Let me）调查

> 结论一句话：**"We need" 不是 persona 锚定出的模型状态，而是"分析型问题形式"触发的语域；
> 提问方式决定思考语态，语态无法被强制或锚定。**
> 本目录记录整条调查链：插件原理审计 → 21,646 块真实数据实测 → 因果对照实验。

调查日期：2026-09-01。数据来源：本机 `~/.dsh/sessions`（681 个 zstd 会话，全部聚合统计，未输出对话原文）。

---

## 0. 缘起

社区（`dsh-anchored-standard` / `dsh-anchored-flash` / `dsh-router-standard`）有一个广泛认知：
**"We need" 思维链效率远超 "Let me" 思维链**，且存在"双吸引子"——spec（we/let's）与 react（let me）
两种稳定形态，可被首轮 persona 锚定，之后路径锁定。

`@a9i5k4/dsh-anchored-monitor`（一个实时监测 + 自动干预插件）正是建立在这套理论上：
实时计算 persona_ratio，进入 react 带就 L1 提示 / L2 重置（persona 换 Minimal + 工具砍到 2 个）/ L3 重启建议。

本次调查检验这条理论链的每一环。

## 1. 插件原理审计（静态）

- 架构：独立 Node 监控进程（127.0.0.1:9301，SSE 推送干预信号）+ DSH host 插件（采集/执行/代理路由）+ Web 客户端（浮层仪表盘）
- 判据：`persona_ratio = count(let me) / (count(正向词) + count(let me))`，<0.2 spec / 0.2–0.5 mixed / ≥0.5 react
- 采集：`llm/stream` 的 reasoning-delta（1s 节流）+ `session/event` 兜底；`text-delta` 另供 CoT 泄漏/停摆守卫（仅告警）
- 干预：L1 建议式 hint 注入 + followup 续跑；L2 `agent.cancel` + `system-prompt/assemble` 换 persona/收缩工具；L3 同 L2 + 重启建议

**审计发现的问题**：

1. **载荷丢失 bug（严重）**：`session-manager.ts` 快照序列化只挑 6 个字段、丢弃 `payload`，而 host 插件只走
   `/api/sessions/:id` 轮询（不订阅 SSE）。实测 SSE 事件带 payload、快照不带 → L1 注入空消息，
   L2 退化为"空 persona + 零工具"（文档声称的是 Minimal 46 字符 + bash/str_replace_editor 双工具）。
   修一行 map 即可：`payload: i.payload`。
2. **词典重复计数**：`we need` / `we'll` 会被 `\bwe\b` 同时命中，正向分母被放大 ~2×，边界阈值静默偏移。
3. **流式增量偷换窗口语义**：`window.size: 20` 在流式源下从"20 个块"变成"20 个 1 秒切片"；
   1s 切块还可能把跨边界的 `let me` 切成 `let` + ` me` 漏计（方向：偏向不触发）。
4. **上游理论已被作者部分撤回**：`dsh-router-standard/docs/apology.md`（2026-08-16）——
   "官方刻意设计双模式——错误"、"论文理论部分（假设 A1–A4）标注作废"、"Pro 与 Flash 不是一回事，不能套用经验"。
   anchored-monitor 的 README/CHANGELOG（08-17~08-19）在其后仍把该理论当既定结论。
5. `EventSource` 在 Node 26 非全局（需 `--experimental-eventsource`）；`context.agent.session`
   依赖未公开于类型定义的运行时字段（DSH 一改即静默失效）。

> 完整代码级细节见 `docs/plugin-audit.md`（含文件行号）。

## 2. 真实数据实测（21,646 个思考块）

抽取方法：解压全部 681 个 `session.jsonl.zstd`，取 `assistant/message` 中 `type==="reasoning"` 的文本。
时间跨度 2026-08-17 ~ 09-01；模型分布：deepseek-v4-flash 17,415 / deepseek-v4-pro 4,227。

### 2.1 整块词频口径（第一版，有缺陷）

- persona_ratio 分布**单峰**：98%+ 压在 react 带（≥0.5）；"过渡带 0.2–0.5 是波谷"很大程度是**小分母算术假象**
  （34–45% 的块标记词 ≤2 个，ratio 只能取 0/0.5/1，中间天然为空）。
- 按分母分层后：Flash 的 spec 质量随分母增大**蒸发**（1.2% → 0.0%），mixed 反增（0.3% → 1.7%），波谷消失。
- "路径依赖"（首块预测后续）看似 100%，基准率 99%（本来就几乎全是 react）——**零增量预测力**。
- 会话内漂移：173 个会话**0 次**波段迁移。模式在会话开始即由系统提示词决定，之后纹丝不动。
- 5 个 Minimal（46 字符）会话 vs 291 个完整提示词会话：ratio 中位 0.000 vs 0.977，**完全分离零重叠**；
  工作量匹配对照（140 个同量级会话）后依然零重叠 → 锚定效应真实存在，但那是 persona 的功劳，不是监控的。

> 这个口径被下一轮修正推翻：整块词频把"模型引用用户问题/讨论该话题"也算进去了，
> 典型污染是 `The user is asking: "如何强制模型使用we need思维链…"` 一块同时刷进两个计数。
> **结论以块首口径为准。**

### 2.2 块首语态口径（最终版）

只取每个思考块**开头**的语态（剥离 `now`/`ok`/`so` 等话语标记后判前缀）：

| 块首 | 数量 | 占比 |
|---|---|---|
| `We need` | 109 | 0.50% |
| `Need to` | 103 | 0.47% |
| `Let me` | 1,236 | 5.69% |
| 两者都不是 | 20,148 | 92.73% |

- **2026-08-17 ~ 08-31 十五天：`We need` 开口总计 7 次**（分散在 5 个会话）。
- **2026-09-01 一天：205 次**，集中在 7 个会话，spec 开口占比 86–100%——全部发生在**今天**。
- 最早稳定出现：**2026-09-01 11:40**，用户问题「你可以查到我们关于插件市场的历史会话吗」（10/10 块 spec 开口）。
- 今天 11:40 起连成一串：12:04 记忆插件检索（15/15）、12:06 sqlite embedding 成本估算（64/64）、
  12:22 竞技场 v2 流程（36/56）、12:57 质疑轮（8/8）、13:31 插件分析（60/60，即当前会话）、13:51 插件检索（12/14）。

**同一天内 SPEC 组与 0% 组的候选变量全部排除**（两组条件完全相同）：

| 变量 | 结果 |
|---|---|
| 系统提示词长度 | 两组都 ~50962 ❌ |
| 工具数 | 两组都 77 ❌ |
| 是否加载 skill | 13:34 加载了却 0%，11:40/12:04/12:57 没加载却 100% ❌ |
| reasoningEffort | high 与 max 两组都有 ❌ |
| 模型 | flash 与 pro 两组都有 ❌ |

唯一未被证伪的相关性：**任务性质**——SPEC 组全是分析/估算/评审/理解型；
0% 组是执行/编码/定点查询型。

## 3. 因果对照实验（2026-09-01 15:06，本目录结论的定因一步）

**同一个对象、同样的活、同样的工具，只改提问动词。** 措辞刻意避开 `we`/`let me`/`need` 以排除污染。

| 组 | 问题（新会话） | 结果 |
|---|---|---|
| A 分析型 | 「为什么 ~/.dsh/sessions 会占用这么大空间？分析一下主要是什么在占空间。」 | **6 个思考块全部以 `We need`/`Need to` 开口**（`session-44eb6ec2`） |
| B 执行型 | 「列出 ~/.dsh/sessions 下各个子目录的大小，按从大到小排序。」 | **0 个思考块**，直接跑 du 输出 878 字表格（`session-fc15a931`） |

间隔 4 分钟，同一环境，结果完全不重叠。B 组不是"let me 模式"而是**根本没进思考模式**。

**定因结论：**
- `We need` 是**问题形式触发的语域**：问"为什么/分析/解释" → 思考块以 `We need`/`Need to` 开口；
  问"列出/做/执行" → 不思考直接干。
- 此前观测到的 `Let me`，更可能是**执行型任务**的思考方式（"让我看下这个文件"），而非"低专注模式"。
- **语态不是可锚定/可强制/可监测漂移的模型状态。** anchored-monitor 干预的变量不在它控制的轴上。

## 4. 对社区的收束

- "we need 效率远高于 let me"的体验是真的，但机制解释反了：
  **分析型任务**驱动 we need 语态，we need 是"分析型任务在思考"的结果/伴随物，不是能力提升的原因。
- "双吸引子 + 三带量化 + 路径依赖"理论：作者本人已部分撤回（见 1.4）；实测不支持三带（见 2.1）。
- 想要 we need 语态：**把问题问成分析型**（为什么/评估/解释/方案对比），不需要换 persona、不需要砍工具。
- anchored-monitor 作为**可视化仪表**可用；作为**自动干预器**在默认场景（完整提示词）下会从第 1 块起
  永久触发 L2，且载荷 bug 使实际效果是"空 persona + 零工具"。

## 5. 复现

```bash
# 全量抽取与块首分类（约 5-10 分钟，输出聚合统计，不输出原文）
node tools/thinking-voice/analyze.mjs

# 快速对照实验（需手动开两个新会话提问，脚本只做判定）
node tools/thinking-voice/classify-session.mjs <session-id或目录>
```

配套文件：

- `docs/plugin-audit.md` — 插件原理审计全文（文件行号级）
- `analyze.mjs` — 全库抽取 + 块首分类 + 每日趋势
- `classify-session.mjs` — 单会话块首语态判定（现场分析用）
- `data/causal-experiment.json` — 对照实验记录（问题原文 + 会话 id + 结果）
- `data/blocks-aggregate.json` — 全库聚合统计（无原文）

原始抽取脚本（`/tmp/analysis/measure.mjs` 等）未纳入本目录，分析逻辑已整合进 `analyze.mjs`。
